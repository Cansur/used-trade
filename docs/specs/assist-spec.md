# 요청 명세 — 상품 등록 AI 보조 (SPEC-1)

> 사람 ↔ AI 인터뷰로 확정한 요구사항. 설계 상세는 ADR-007 (SPEC-2) 에서 다룬다.
> 상태: **확정** (2026-10-29). 단 2-4 재시도 정책은 MEAS-5 결과로 최종 확정.

<br>

## 1. 기능 개요

판매자가 상품 등록 화면에서 제목·설명을 입력하면 서버가 **카테고리**와 **가격 범위**를 추천한다.<br>
추천은 보조 정보다. 판매자가 채택 여부를 정하고, AI 가 실패해도 상품 등록은 된다.

<br>

## 2. 확정 요구사항

### 2-1. 결과 전달 방식 — 동기 + 타임아웃 + 폴백 (2026-10-28)

- 클라이언트가 추천 API 를 호출하면 **같은 HTTP 응답에 추천 결과를 담아** 돌려준다
- LLM 호출에 타임아웃을 둔다. 시간 안에 답이 없거나 응답이 잘못되면 **폴백 결과** (키워드 규칙 카테고리 + DB 기반 가격 범위) 를 돌려준다
- 응답에 추천 출처를 표시한다 (예: `source: LLM | FALLBACK`)
- 서버는 Java 21 가상 스레드로 요청을 처리해, LLM 을 기다리는 동안 OS 스레드를 점유하지 않게 한다

**비동기 (202 + 조회 / WebSocket push) 를 택하지 않은 이유**
- 사용자는 등록 버튼을 누르기 전에 추천을 확인한다. 결과를 나중에 받아도 이득이 없다
- 사용자 체감은 동기든 비동기든 같다 (둘 다 로딩 표시, 화면 조작 가능). 차이는 서버 자원과 구현 복잡도뿐
- 서버 자원 문제 (대기 중 스레드 점유) 는 가상 스레드 + 타임아웃으로 줄인다. 비동기는 결과 저장소와 전달 경로가 추가로 필요해 복잡도만 늘어난다
- 이 판단은 측정으로 뒷받침한다 → 3절 측정 요구

### 2-2. 입력 범위 — 1차는 제목·설명만 (2026-10-28)

- LLM 에 보내는 입력은 제목 + 설명 텍스트
- **제목은 필수, 설명은 선택** (2026-11-08) — 판매자는 제목을 먼저 쓰므로 그 시점에 추천을 받을 수 있어야 한다. 제목만일 때 정확도가 얼마나 떨어지는지는 MEAS-2 에서 비교한다
- 상품 등록 API 는 그대로 설명 필수다. 추천 요청만 설명을 생략할 수 있다
- 이미지는 1차 범위 밖 — LLM 이미지 입력은 비용·지연이 크고, 현재 이미지 저장소가 Mock 이라 실제 이미지가 없다

<br>

### 2-3. LLM — Claude Haiku 5.5 (2026-10-29)

- 실제 어댑터는 Claude Haiku 5.5. tool use 로 JSON 형식을 강제한다
- 실제 호출은 정확도 평가셋 + 재시도 측정 + 시연에만. 개발·부하·장애 테스트는 가짜 LLM
- API 키는 환경 변수로만 ([policies.md](../policies.md) 5절)

### 2-4. 타임아웃 / 재시도 — 전체 3초 예산 안에서 1회 (2026-10-29, 잠정)

- 요청 하나당 전체 시간 예산 3초. 넘으면 폴백
- 빠른 실패 (연결 오류, 429/5xx/529) 또는 형식 오류 (깨진 JSON, 없는 카테고리) 이고 **남은 예산이 충분하면** 1회 재시도
- 타임아웃은 재시도하지 않는다 — 느린 원인 (서버 부하) 이 그대로일 가능성이 높아 대기만 늘어난다는 가설
- SDK 내장 재시도는 끄고 코드에서 직접 제어한다 (예산 계산이 틀어지지 않게)
- **잠정** — "타임아웃 후 재시도는 효과가 없다" 는 가설은 MEAS-5 로 실측 후 확정. 결과에 따라 타임아웃 재시도 포함 여부를 바꾼다

### 2-5. 정확도 평가셋 — 100개 (2026-10-29)

- 10 카테고리 × 10개, 애매한 케이스 일부 포함. 정답 라벨은 사람이 붙인다

### 2-6. 가격 시드 데이터 — 수작업 기준값 + 합성 확장 (2026-10-29)

- **기준값**: 카테고리 10개 × 대표 품목 6개 = 60줄. 사람이 중고 시세를 직접 보고 "사용감 보통" 기준 가격 범위를 기록 → `src/main/resources/seed/price-anchors.csv`
- **합성 확장**: 생성기가 기준값을 중심으로 상태별 보정 (예: 거의 새것 +10%, 사용감 많음 −15%) + 분포에 따른 무작위 가격 + 제목 템플릿으로 품목당 수십 건 생성. 이상치 (급처, 과도한 호가) 를 일부러 섞는다. 랜덤 시드 고정으로 재현 가능
- 생성 데이터는 벤치마크용 기존 데이터 (로컬 약 10만 건) 와 구분한다
- **가격이 비어 있거나 0 인 줄은 생성기가 건너뛴다** — 매물이 없거나 가격대가 제각각인 품목은 note 에 이유를 남기고 비워 둔다 (2026-10-30 조사: 4줄. 카테고리별 기준값은 4개 이상 유지)
- **범위가 넓은 품목** (조사 결과 다수가 max/min 3배 초과, 예: 피규어 3만~100만) 은 그대로 둔다. 품목 자체가 이질적이라는 조사 결과이며, 가격 추천은 표본 편차가 크면 신뢰도를 낮게 표시하거나 범위를 넓게 보여준다 → ADR-007 에서 규칙 확정
- 파일은 UTF-8. 엑셀로 저장하면 BOM 이 붙을 수 있으므로 로더는 BOM 을 허용한다
- **출처 원칙**: 실거래 데이터 아님 — "수작업 기준값 기반 합성 데이터" 로 문서에 명시. 플랫폼 크롤링·대량 수집 금지 (데이터베이스권 침해 판단 사례 있음), 기준값 조사 시 URL·판매자 정보는 기록하지 않는다
- 이유: 이 기능에서 보여줄 것은 시세의 정확도가 아니라 **가격 계산 설계** (유사 상품 중앙값, IQR 이상치 제거, 표본 부족 시 폴백). 데이터는 그럴듯하면 되고 출처가 깨끗해야 한다

**`price-anchors.csv` 컬럼**

| 컬럼 | 내용 | 예 |
|---|---|---|
| category | 시드 카테고리명 (`CategoryDataInitializer` 와 동일) | 전자기기 |
| item | 대표 품목 | 아이폰 15 128GB |
| keywords | 제목 생성·유사 매칭용 별칭, `\|` 구분 | 아이폰15\|iphone15 |
| price_min / price_max | "사용감 보통" 기준 시세 범위, 원 단위 정수 | 700000 / 850000 |
| checked_at | 조사한 날짜 | 2026-10-30 |
| note | 자유 메모 (선택) | 배터리 성능에 따라 편차 큼 |

## 3. 측정 요구

- 가짜 LLM 에 지연 (예: 3초) 을 주입한 상태에서 추천 API 부하 → **다른 API (예: 상품 목록) 의 p95** 를 플랫폼 스레드 / 가상 스레드로 비교
- 타임아웃·깨진 응답 비율별 추천 API 성공률 (폴백 포함) 과 p95 — MEAS-1
