# 작업 규칙

> 사람과 AI 가 모두 지킨다. 코드 컨벤션 상세는 [guides/project-structure.md](guides/project-structure.md) 와 `CLAUDE.md` 컨벤션 절.

<br>

## 1. 작업 시작 / 종료

**시작 전**
1. [index.md](index.md) → [roadmap.md](roadmap.md) → [todo.md](todo.md) 순서로 읽는다
2. 작업 대상 도메인의 ADR / Guide 를 읽는다
3. 이번에 처리할 TODO ID 를 "진행 중" 으로 옮긴다

**종료 시** (같은 커밋 또는 같은 PR 에 포함)
1. [todo.md](todo.md) — 완료 근거와 함께 체크, "완료" 로 이동
2. [status.md](status.md) — 기능·한계 표 갱신 + 변경 기록 한 줄
3. 설계 결정이 있었으면 ADR 갱신 또는 신규 작성
4. 방향이 바뀌었으면 [roadmap.md](roadmap.md) 갱신

<br>

## 2. TODO 규칙

- ID 접두어: `SPEC` 명세 / `DEV` 개발 / `MEAS` 측정 / `FLOW` AI 워크플로우 / `DOC` 문서 / `WIKI` 위키 / `HOLD` 보류
- ID 는 재사용하지 않는다. 항목이 쪼개지면 `DEV-4a`, `DEV-4b`
- **완료 근거 없는 체크는 무효** — 파일 경로, 커밋, PR, 테스트명, 측정값 중 하나 이상
- 하지 않기로 한 항목은 지우지 않고 `~~취소선~~` + 이유

<br>

## 3. 위키 작성

- 큰 그림과 구조만. 코드 상세는 쓰지 않는다 (코드가 맥락)
- 링크는 표준 Markdown `[텍스트](파일.md)` — GitHub 와 Obsidian 양쪽에서 동작해야 한다. `[[위키링크]]` 금지
- 검색 인프라 (RAG 등) 는 두지 않는다. 인덱스 문서의 링크로 찾는다
- `.obsidian/` 은 커밋하지 않는다

<br>

## 4. 코드 안의 맥락 — `AI-NOTE`

- 형식: `// AI-NOTE: <코드만 봐서는 알 수 없는 제약 또는 이유>`
- 쓰는 경우: 지우면 안 되는 이유, 숨은 순서 의존, 외부 제약, 일부러 한 비직관적 선택
- 쓰지 않는 경우: 코드를 다시 설명하는 내용, 설계 배경 (그건 Javadoc 이나 ADR)
- 검색: `grep -rn "AI-NOTE" src`

<br>

## 5. 외부 의존성

- 외부 시스템 (PG, 저장소, LLM) 은 Port 인터페이스 뒤에 둔다 — 예: `PaymentGatewayPort`
- 구현은 실제 어댑터 + 데모용 Mock + 테스트용 장애 주입 구현 (Controllable)
- 외부 의존성이 실패해도 핵심 흐름은 성공해야 한다 (폴백 필수)
- API 키 등 시크릿은 `.env` / 환경 변수로만. 코드·문서에 넣지 않는다

<br>

## 6. 측정 기록

- 수치는 항상 **조건 + 결과 + 재현 방법** 을 함께 적는다 (예: N, 데이터 건수, 명령어, 테스트명)
- Before / After 비교가 가능하면 둘 다 남긴다
- 측정하지 않은 것은 "가설" 또는 "체감" 으로 명시한다. 과장 금지
