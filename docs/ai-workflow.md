## 왜 나누는가

같은 모델이 만들고 검수하면 자기 의도에 맞춰 검수해서, 다른 방향에서 들어오는 문제를 놓친다는 가설.<br>
사람 개발자가 자기 코드를 리뷰할 때와 같은 문제다. 측정 전까지는 가설로만 다룬다.

<br>

## 역할

| 역할 | 담당 | 권한 |
|---|---|---|
| 사람 | 이선재 | 요구사항 결정, 반복 루프 중재, 최종 머지 |
| 작업 AI | Claude Code | 명세 · 코드 · 테스트 · 위키 작성 및 수정 |
| 검수 AI (평소) | Claude Code 의 **새 맥락 검수 에이전트** | **읽기 전용** — 지적과 지시만, 직접 수정 금지 |
| 검수 AI (실험) | **웹 Gemini** (gemini.google.com, Plus 요금제) | 읽기 전용 — diff + 검수 지시문을 붙여넣어 판정만 받음 |

- 평소 검수는 작업 맥락을 모르는 새 에이전트에게 맡긴다 — 작업 의도에 끌려가지 않게 하기 위해
- 다른 모델 계열 (Gemini) 은 FLOW-2 실험에서만 쓴다
- 검수 AI 가 직접 고치지 않는 이유: 한 모델의 코드 스타일을 유지하기 위해

### 비용 원칙 — 추가 지출 0원

- 유료 Codex / API 키 검수는 쓰지 않는다. 이미 쓰는 구독 (Claude Code, Gemini Plus) 안에서만
- Gemini CLI 는 Plus 요금제를 지원하지 않는다 (CLI 는 AI Pro / Ultra 만, 무료·Google One 은 2026-06-18 부터 Antigravity CLI 로 전환 — geminicli.com 요금 문서, 2026-10-26 확인). 그래서 웹으로 쓴다

## 흐름

```txt
SPEC (명세)  작업 AI 작성 ⇄ 검수 AI → APPROVE
   ↓  DEV TODO + QA 테스트 리스트
DEV (개발)   작업 AI 구현 ⇄ 검수 AI → APPROVE   (단위·통합 테스트 통과 포함)
   ↓
QA          QA 테스트 리스트 실행 → 결과 증거 → 검수 AI 판정 PASS / FAIL
   ↓  FAIL 이면 TODO 재작성부터
WIKI        status / todo / ADR 갱신 ⇄ 검수 AI → APPROVE
```

- 검수 판정: `APPROVE` / `REJECT` + 수정 지시
- 검수 기준 (DEV): ① 완료 근거대로 실제 작업했는가 ② TODO 항목의 의도에 맞는가
- **같은 주제의 지적이 3회 반복되면 멈추고 사람이 중재한다**

- 검수 왕복 기록은 PR 설명 또는 `docs/reviews/<TODO-ID>.md` 에 남긴다 (작업 → REJECT → 수정 → APPROVE 순서)

## FLOW-2 실험 설계

질문: 검수가 문제를 더 잘 잡는 이유가 **모델이 달라서**인가, **맥락이 분리돼서**인가?

| 조건 | 검수자 | 맥락 |
|---|---|---|
| C1 자기 검수 | Claude | 작업한 세션 그대로 (의도를 앎) |
| C2 새 맥락 | Claude | 새 에이전트 (diff + 지시문만) |
| C3 다른 모델 | 웹 Gemini | diff + 지시문만 |

- 버그를 심은 diff 약 20개 — 종류를 섞는다 (동시성, 경계값, 예외 누락, 검증 누락, 명세와 다른 동작)
- 세 조건 모두 **같은 diff, 같은 검수 지시문**
- 기록: 조건별 발견 수, 놓친 버그, 오탐 (버그 아닌 것을 지적)
- 한계를 결과와 함께 적는다: 표본이 작다, 버그를 심은 사람이 작업자와 같다, 모델 버전에 따라 달라질 수 있다
